# beta-smoke-gate Specification

## Purpose

Define the evidence required to decide whether the current FindYourPet candidate can be distributed to Beta testers.

## ADDED Requirements

### Requirement: Candidate build and automated checks

The Beta gate SHALL verify the repository preflight, candidate build metadata, debug unit tests, and required Android build tasks before environment-dependent testing begins.

#### Scenario: Repository and OpenSpec preflight passes

- **WHEN** the gate starts on the candidate branch
- **THEN** Git status, branch, base commit, and applicable OpenSpec validation are recorded with no unapproved working-tree changes

#### Scenario: Required debug tasks pass

- **WHEN** `testDebugUnitTest` and `assembleDebug` are executed through the repository Gradle wrapper
- **THEN** both tasks complete successfully and their commands and results are included in the Beta report

#### Scenario: Candidate metadata is inspected

- **WHEN** the Beta candidate is selected
- **THEN** `applicationId`, `versionCode`, `versionName`, build variant, signing state, and tracked-secret review are recorded

### Requirement: Installation, launch, and authentication

The Beta gate SHALL verify that the candidate installs, launches, reaches the primary screen, and enforces the authenticated and unauthenticated access boundary.

#### Scenario: Candidate installs and launches

- **WHEN** the candidate is installed on a compatible physical device or emulator and launched
- **THEN** installation succeeds, startup does not crash or hang, and the primary screen is reachable

#### Scenario: External device is unavailable

- **WHEN** no compatible physical device or emulator is available
- **THEN** installation, launch, and device-dependent checks are marked `BLOCKED` with the required environment action

#### Scenario: Authenticated user reaches authorized flows

- **WHEN** a valid test user signs in
- **THEN** the user can reach the authorized publishing, sighting, activity, alert, reporting, and blocking flows required by this gate

#### Scenario: Unauthenticated user is restricted

- **WHEN** a signed-out user attempts to publish, send a sighting, report content, block a user, or access private information
- **THEN** the protected operation is rejected without an unauthorized data write or crash

### Requirement: Core publishing and sighting flows

The Beta gate SHALL verify that publishing and two-user sighting flows preserve the required identifiers, ownership, content, location, time, and persistence behavior.

#### Scenario: User publishes a lost-pet post

- **WHEN** an authenticated user completes the required post form with a photo and location and submits it
- **THEN** the post is persisted, appears in the expected feed, and the post-publication navigation remains usable

#### Scenario: User submits one sighting

- **WHEN** User A opens User B's pet post, completes the sighting form, and submits it
- **THEN** exactly one sighting is created with a stable `sightingId`, correct owner and reporter, notes, location, and date/time

#### Scenario: Sighting submission fails

- **WHEN** the sighting operation encounters a backend, permission, or availability error
- **THEN** no duplicate or partial sighting is created, the UI presents a controlled error, and diagnostic details are recorded separately

### Requirement: Alert, activity, and sighting-detail navigation

The Beta gate SHALL verify that alerts and activity use `sightingId` to open the existing sighting detail, preserve back navigation, and do not route through Chat.

#### Scenario: Alert opens the correct sighting

- **WHEN** User B receives the alert generated by User A's sighting and taps it
- **THEN** the alert identifies the correct user, carries `sightingId`, opens the matching sighting detail, and Back returns correctly

#### Scenario: Activity opens the selected sighting

- **WHEN** User B selects the sighting from Activity
- **THEN** Activity loads the correct record by `sightingId`, supports loading, empty, and error states, and opens the same sighting-detail screen

#### Scenario: Sighting detail shows required data

- **WHEN** the selected sighting has available details
- **THEN** the screen shows the pet, location, date/time, comment, photo when available, and `Ver ubicación` action without a Chat composer or conversation history

### Requirement: Content reporting and user blocking

The Beta gate SHALL verify moderation actions, ownership, persistence, cancellation, and enforcement of a user block across subsequent sighting attempts.

#### Scenario: User reports content

- **WHEN** User B selects a reason from sighting detail and confirms the report
- **THEN** one report is created with initial status `PENDING`, while canceling creates no report and reporting does not delete the sighting

#### Scenario: User blocks another user

- **WHEN** User B blocks User A after receiving a sighting
- **THEN** the block is persisted and historical sightings remain available to User B

#### Scenario: Blocked user attempts another sighting

- **WHEN** User A attempts another sighting for User B after the block is active
- **THEN** the operation is rejected, no sighting or alert is created, and no Chat data is created

### Requirement: Chat remains functionally absent

The Beta gate SHALL verify that the current sighting and moderation flows do not create or require new Chat sessions, messages, message subcollections, `chatId`, or active Chat navigation.

#### Scenario: New sighting creates no Chat data

- **WHEN** a new sighting is submitted and its downstream alert is processed
- **THEN** no `ChatSessionEntity`, `ChatMessageEntity`, `chatSessions` document, message subcollection, or new Chat message is created

#### Scenario: Critical screens contain no active Chat flow

- **WHEN** a tester navigates through Home, Alerts, Activity, sighting detail, reporting, and blocking
- **THEN** no Chat composer, reply action, message bubble, conversation history, or active Chat destination is reachable

### Requirement: Firestore security and critical-query validation

The Beta gate SHALL validate authorization and operational access for the Firestore collections and queries used by the Beta flows.

#### Scenario: Protected collections reject unauthorized access

- **WHEN** unauthenticated or cross-user test operations target `users`, `petPosts`, `sightings`, `contentReports`, `userBlocks`, or `notifications`
- **THEN** reads and writes are rejected unless the operation is explicitly authorized for that user and ownership context

#### Scenario: Rules contain no global allow

- **WHEN** the deployed or candidate Firestore rules are inspected
- **THEN** no critical collection is governed by an unrestricted equivalent of `allow read, write: if true`

#### Scenario: Critical queries execute

- **WHEN** Home, Alerts, Activity, and sighting flows execute their real Firestore queries
- **THEN** each required query succeeds without a missing-index or permission error, or the gate records the exact failure as `FAIL`

### Requirement: Error, persistence, and theme smoke validation

The Beta gate SHALL verify controlled error presentation, relevant Room migration tests, and basic Light/Dark usability for critical surfaces.

#### Scenario: Technical errors are bounded for users

- **WHEN** a critical flow encounters `FAILED_PRECONDITION`, `PERMISSION_DENIED`, `UNAVAILABLE`, or a Firebase exception
- **THEN** the user sees a controlled message rather than the raw technical error text, while diagnostics retain enough detail for investigation

#### Scenario: Room validation remains green

- **WHEN** the existing Room migration and persistence tests run
- **THEN** required migrations remain valid and no destructive migration is introduced by the Beta candidate

#### Scenario: Critical surfaces work in both themes

- **WHEN** a tester smoke-checks Home, bottom navigation, dialogs, errors, and empty states in Light Mode and Dark Mode
- **THEN** text remains legible, contrast is usable, CTAs are reachable, and no theme-specific crash or blocking overlap is observed

### Requirement: Beta report and final decision

The Beta gate SHALL produce a report mapping every mandatory area to evidence and SHALL assign only `PASS`, `BLOCKED`, or `FAIL` according to the defined decision rules.

#### Scenario: Complete gate produces PASS

- **WHEN** build, tests, installation, authentication, critical flows, security checks, query checks, Chat absence, and required smoke tests all pass
- **THEN** the report assigns `PASS` and states that the candidate is eligible for Beta distribution

#### Scenario: External prerequisite prevents completion

- **WHEN** an external dependency prevents a mandatory check from running and no application defect is established
- **THEN** the report assigns `BLOCKED`, names the dependency, records evidence, and lists the action needed to resume

#### Scenario: Reproducible defect prevents distribution

- **WHEN** a mandatory check exposes a reproducible build, startup, functional, security, persistence, navigation, or stability defect
- **THEN** the report assigns `FAIL`, identifies the affected area and reproduction evidence, and states that the candidate is not ready for Beta distribution
