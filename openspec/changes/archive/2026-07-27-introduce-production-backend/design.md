## Context

FindYourPet ya tiene Firebase Authentication, Cloud Firestore y reglas iniciales disponibles, pero los flujos principales siguen dependiendo de Room para lectura, demo seed y estado local. `PetRepository` escribe algunos documentos en Firestore, aunque las pantallas observan Room, las sesiones de chat se describen como locales y las notificaciones no son una bandeja compartida por usuario.

El cambio introduce un backend de produccion para datos compartidos. La identidad canonica sera `request.auth.uid`; Firestore sera la fuente de verdad para publicaciones, avistamientos, chats y notificaciones; Room quedara como cache local opcional sin autoridad para permisos.

## Goals / Non-Goals

**Goals:**

- Definir colecciones Firestore estables para usuarios, publicaciones, avistamientos, chats, mensajes y notificaciones.
- Reemplazar lecturas y escrituras locales por repositorios remotos observables.
- Garantizar que una publicacion creada por un usuario autenticado sea visible para otros usuarios autenticados.
- Garantizar que avistamientos, chats y mensajes solo sean legibles por participantes autorizados.
- Exponer estados de carga, error, datos desde cache/remoto y escrituras pendientes en ViewModels.
- Mantener Room como cache o seed de demo aislado, sin decidir ownership ni permisos.
- Validar reglas Firestore antes de usar datos reales.

**Non-Goals:**

- Implementar subida real de imagenes a Storage; `photoUri` puede seguir siendo URL/URI hasta `add-real-photo-upload`.
- Implementar captura real de GPS; coordenadas siguen dependiendo del flujo actual hasta `add-location-capture`.
- Implementar push notifications FCM; esta etapa cubre notificaciones persistentes in-app.
- Implementar cifrado extremo a extremo de mensajes.
- Migrar datos demo existentes a cuentas reales automaticamente.
- Permitir feed anonimo o lectura publica sin autenticacion.

## Decisions

### Decision: Firebase Auth + Cloud Firestore as the production backend

Use Firebase Authentication for identity and Cloud Firestore for shared data because the project already declares Firebase dependencies, has setup docs and contains initial `firestore.rules`. This avoids introducing a second backend stack during the highest-risk data transition.

Alternatives considered:

- Custom REST backend: more control, but adds server hosting, auth token verification and deployment complexity before MVP.
- Supabase/Postgres: strong relational model, but conflicts with the existing Firebase/Auth direction and would require replacing current setup work.
- Keep Room plus manual export/import: cannot satisfy shared publications, real chat or central authorization.

### Decision: Firestore data model with explicit ownership and membership

Use top-level collections for shared resources:

- `users/{uid}`: private profile and safe public profile fields. The document id MUST equal Firebase `uid`.
- `petPosts/{postId}`: shared pet publication. Includes `ownerId`, pet fields, status, visibility fields, coarse location label and optional coordinates with privacy controls.
- `sightings/{sightingId}`: immutable sighting report. Includes `postId`, `ownerId`, `reporterId`, location fields, photo URI, notes and timestamps.
- `chatSessions/{chatId}`: one conversation for a post owner and reporter. Includes `postId`, `ownerId`, `reporterId`, last message metadata and contact sharing flags.
- `chatSessions/{chatId}/messages/{messageId}`: append-only messages from session participants.
- `users/{uid}/notifications/{notificationId}`: per-user notification inbox generated by client writes during this phase.

Documents use server-side timestamps where possible and keep user ids immutable after creation. Chat ids SHOULD be deterministic from `postId` and `reporterId` to prevent duplicate sessions.

Alternatives considered:

- Nest sightings under posts: simpler ownership lookup, but harder for owner-wide inbox queries.
- Store notifications in a global collection: easier collection group queries, but requires every query and rule to filter recipient correctly.
- Store messages in a top-level collection: simpler global indexing, but weaker locality and more rule reads.

### Decision: Repository contract exposes remote sync state

Introduce remote repository methods that return observable state instead of raw Room flows. UI models SHALL distinguish loading, empty, error, remote data, cache data and pending writes. Firestore snapshot metadata can mark whether a result came from cache and whether local writes are pending.

Alternatives considered:

- Keep current Room-only `Flow<List<Entity>>`: simple, but hides remote errors and makes stale local data look authoritative.
- Use one-shot reads only: easier to implement, but does not support shared chat/feed expectations.

### Decision: Room remains a cache, not an authority

Room can store the latest remote projection for responsive UI and offline read behavior. Any create/update/delete that affects production data MUST go through Firestore and be authorized by rules. Room writes triggered by remote snapshots are cache updates only.

Alternatives considered:

- Remove Room immediately: less complexity, but a bigger UI/repository rewrite and weaker offline continuity.
- Keep Room as primary source: fails central persistence and authorization requirements.

### Decision: Security rules define the backend contract

Rules SHALL require `request.auth != null`, validate owner/member fields on create, prevent owner/member reassignment on update and deny all unknown collections. Pet post writes are owner-only; sightings are create-only for authenticated reporters and readable by owner or reporter; chat sessions/messages are readable and writable only by participants; notifications are readable and mutable only by the recipient.

Sighting fan-out SHALL be committed as a single Firestore batch: sighting, chat session, initial message and owner notification either all persist or all fail. Rules validate the newly-created or merged chat session with `getAfter()` before allowing the initial message so the batch remains atomic without permitting non-participant messages.

Alternatives considered:

- Enforce permissions only in the Android client: insufficient because clients can be modified.
- Allow broad authenticated reads for all collections: acceptable for public post feed only, unsafe for sightings, messages, contact fields and notifications.
- Split sighting fan-out into sequential client writes: simpler message rules, but allows partial backend state if the app or network fails between writes.

### Decision: In-app notifications first, push later

This stage creates persistent notification documents under the recipient user. Android system notifications may continue to be local, generic and free of sensitive content. FCM delivery is deferred to a later push-notification change.

Alternatives considered:

- Add FCM now: useful, but expands permissions, tokens, backend triggers and privacy review beyond this change.
- Keep only local notifications: does not work across devices or accounts.

## Risks / Trade-offs

- [Risk] Firestore rules and client mappers drift apart -> Mitigation: model fields in constants/DTOs, add rules validation docs and unit tests for repository mapping.
- [Risk] Offline cache may show stale data as if it were fresh -> Mitigation: expose cache/remote metadata and pending write state in UI.
- [Risk] Client-created notifications can be abused -> Mitigation: restrict recipient and event fields in rules now; later move privileged fan-out to Cloud Functions if needed.
- [Risk] Existing demo seed data may leak into authenticated flows -> Mitigation: isolate seed data behind demo mode and never derive ownership from `owner_1`, `finder_1` or other fixed ids.
- [Risk] Shared feed may expose too much owner contact or exact location -> Mitigation: split public post fields from private contact/location fields and require explicit owner-controlled reveal.
- [Risk] Firestore query requirements may need indexes -> Mitigation: document required query shapes and add indexes when emulator/console reports them.

## Migration Plan

1. Add remote DTOs/mappers for backend documents while keeping existing Room entities stable.
2. Introduce repository interfaces for posts, sightings, chats and notifications with sync state wrappers.
3. Implement Firestore listeners and writes behind the existing ViewModel surface.
4. Update Room writes so they mirror remote snapshots only, not decide permissions.
5. Replace demo seed activation in authenticated flows with empty/backend state.
6. Update `firestore.rules` for all collections and add validation cases.
7. Run debug build, unit tests and Firestore rules validation in emulator or a non-production Firebase project.

Rollback strategy: keep the existing Room-backed demo path available for non-production builds and gate remote repositories behind Firebase availability. If rules or remote sync block critical flows, disable the production backend path while preserving local demo behavior for development only.

## Open Questions

No blocking open questions. Push delivery, real photo upload and real GPS capture remain intentionally deferred to later changes already represented in the roadmap.
